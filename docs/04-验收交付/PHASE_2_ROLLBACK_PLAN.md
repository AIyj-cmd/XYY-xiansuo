# 阶段二回滚计划：业务一致性基线

日期：2026-07-30
原则：先停写并保全当前数据，再按故障类型回退；迁移 `003` 不提供破坏性向下迁移。

## 1. 回滚准备

- 上线前保存上一受批准应用制品、本次发布制品、环境变量快照、实际 `DB_PATH`、数据库一致性备份、上传目录和迁移日志。
- 在隔离副本验证备份可打开，并记录 `001`、`002`、`003` 的版本、描述和 checksum。
- 保留阶段一安全要求；不得通过恢复固定默认密码、关闭实时角色校验或关闭 SQLite 外键来完成回滚。

## 2. 回滚触发条件

- `003` 迁移失败、checksum 冲突、`integrity_check` 非 `ok` 或 `foreign_key_check` 非空。
- member 可伪造负责人、停用用户可被分配、同 owner 重复审计。
- 批量转移出现部分成功，或公海重复认领产生重复审计。
- 跟进新增、编辑、删除后派生时间错误，或方案 B 未正确清空最后一条跟进的派生值。
- 原 API 路径、鉴权行为或 `{ code, msg, data }` 包络出现阻断性回归。
- 服务进入重启循环或数据库错误持续增加。

## 3. 回滚步骤

### A. `003` 失败且业务写入尚未恢复

1. 保持服务停止，不重复修改迁移记录。
2. 保存失败数据库、WAL/SHM 和日志现场用于诊断。
3. 从上线前完整备份恢复到新的明确路径，并验证可打开。
4. 切回上一受批准制品和恢复后的 `DB_PATH`。
5. 执行完整性、外键及核心 API 冒烟后再恢复流量。

### B. `003` 成功但应用回归，尚未恢复写入

1. 停止服务并保存当前数据库快照。
2. 优先在数据库副本验证旧应用是否兼容 `003` 新增列和迁移记录；通过后可仅回退应用制品并保留升级后的数据库。
3. 若旧应用不兼容或回填结果异常，恢复上线前完整备份。
4. 不得手工删除列、索引或 `schema_migrations` 中的 `003` 记录。

### C. 已恢复业务写入

1. 立即停止写入并记录故障开始时间。
2. 保存当前数据库完整快照，避免丢失上线后新增线索、跟进和审计。
3. 优先回退应用制品并保留当前数据库；在隔离副本验证后再切换。
4. 如必须恢复上线前备份，先完成上线后新增/变更记录的差异清单和业务对账方案；未经业务负责人确认不得覆盖。
5. 数据合并或人工修复后重新执行完整性、外键、负责人审计和跟进派生抽查。

## 4. 回滚验证

- 服务稳定且健康检查通过。
- 登录、当前用户、实时角色和停用行为仍满足阶段一安全基线。
- 数据库路径正确，`integrity_check=ok`、`foreign_key_check` 为空、应用连接 `foreign_keys=1`。
- 线索、跟进和审计记录数与备份/对账结果一致。
- member 不能伪造负责人，停用负责人被拒绝。
- 单条、批量和公海接口不产生重复审计或部分成功。
- 跟进派生字段符合当前运行制品的批准规则。
- 所有 API 错误响应保持 `{ code, msg, data }`。

## 5. 回滚后记录

记录回滚原因、时间、操作者、旧/新制品、数据库快照、丢失或合并的数据范围、验证结果和后续修复负责人。未经重新评审和副本演练，不得再次上线同一失败制品。
