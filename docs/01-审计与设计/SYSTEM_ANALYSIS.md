## 2. 系统定位与现有业务

XYY-xiansuo 是新亦源内部线索登记、客户跟进和销售管理系统。现有系统已经覆盖：

- 登录、个人资料和密码修改；
- 用户管理；
- 线索创建、列表、详情、编辑、软删除和恢复；
- 单条和批量负责人转移；
- 跟进记录、标签、收藏、备忘；
- 线索池及认领；
- 工作台统计；
- Excel 导入导出；
- 站内通知列表。

线索系统是唯一业务事实来源。拟新增的普通微信和 DeepSeek 都只能作为外围通知、对话和辅助分析能力，不能替代现有页面、权限和业务操作。

## 3. 前端实际结构

### 3.1 技术框架

前端位于 `app/`：

- UniApp；
- Vue 3 Composition API；
- TypeScript；
- Pinia；
- Vite；
- 同时配置 H5 和微信小程序构建。

依赖中使用的是 UniApp alpha 版本，后续开发应先固定并验证构建环境，不能仅凭版本号假设升级兼容。

### 3.2 页面结构

`app/src/pages.json` 当前登记：

- 登录；
- 线索列表、详情、新增/编辑；
- 工作台；
- 线索池；
- 消息通知；
- 备忘录；
- 我的；
- 管理首页、用户、回收站、导入。

底部主导航为线索、工作台、线索池、我的。现阶段没有 AI 页面、拜访计划页面、通知规则页面或微信绑定页面。

### 3.3 状态管理

Pinia 当前只集中维护用户信息和 JWT。Token 同时持久化在 `uni` 本地存储。页面级筛选、表单和列表状态主要由各页面自行维护，没有全局业务数据缓存。

这意味着后续 AI 和通知页面可以延续“后端为事实源、页面短状态”的方式，不需要为了本次扩展引入新的复杂状态框架。

### 3.4 API 调用

`app/src/utils/request.ts` 统一使用 `uni.request`：

- 请求前从本地存储读取 token；
- 通过 `Authorization: Bearer ...` 传递；
- 401 时清理登录状态；
- 没有 Axios、GraphQL 或前端直连数据库。

文件下载同样使用 Authorization header，没有把 token 拼到 URL。后续 AI 请求和通知配置应继续走统一封装，前端不得直连 DeepSeek 或微信服务。

### 3.5 已发现的前端基线差异

线索列表快捷跟进包含“邮件”，但详情页、后端校验和数据库 CHECK 只允许：

```text
电话、微信、拜访、其他
```

该差异会导致快捷入口提交失败。它是独立的基线问题，通知和 AI 模块不得私下添加兼容值；开发前应统一产品枚举并迁移/测试。

## 4. 后端实际结构

### 4.1 技术栈与启动方式

后端位于 `server/`：

- Node.js 22.13+；
- Fastify 5；
- TypeScript / ESM；
- Zod 请求校验；
- `node:sqlite` 同步驱动；
- `jose` JWT；
- `@fastify/static` 同源托管 H5；
- `@fastify/multipart` 处理上传；
- ExcelJS 处理导入导出。

当前是单进程、单 SQLite 连接的模块化服务，没有消息队列、后台 worker、定时任务框架或独立 AI 服务。

### 4.2 路由模块

当前路由文件：

| 模块 | 主要职责 |
| --- | --- |
| `auth.ts` | 登录、当前用户、改密 |
| `users.ts` | 用户管理 |
| `leads.ts` | 线索、跟进、批量操作、公海、审计/关联数据 |
| `dashboard.ts` | 工作台统计 |
| `notifications.ts` | 动态查询站内转移和逾期项 |
| `tags.ts` | 标签 |
| `memo.ts` | 备忘 |
| `import_export.ts` | Excel 导入导出 |
| `upload.ts` | 图片上传 |
| `health.ts` | 健康检查 |

路由直接使用 `getDb()` 执行 SQL，没有 ORM、Repository 或正式 migration runner。新增事件、通知和 AI 权限时，需要抽出内部服务边界，但不应重写所有现有路由。

### 4.3 鉴权现状

JWT 有效期为 7 天，系统角色只有 `admin` 和 `member`。

当前工作区的认证中间件在每次请求中按 token 的 `id` 查询：

```text
id、username、name、role、is_active
```

并以数据库结果重建 `request.user`，所以当前工作区已消除“旧管理员 JWT 在角色降级后继续保留管理员权限”的问题。

但当前已提交版本只从数据库读取 `is_active`，`role`、`name`、`username` 仍来自旧 JWT。该修复尚未提交，生产是否部署未知。后续基线必须：

1. 将 JWT 只视为身份凭证；
2. 每次认证使用数据库中的 id、username、name、role、is_active；
3. 为角色降级、停用和删除用户补回归测试；
4. 在发布清单中验证实际运行 commit。

### 4.4 数据访问方式

业务 SQL 直接位于路由中。部分写操作由多条 SQL 组成，但没有统一事务服务。例如单条编辑会先读旧值、更新，再逐字段写审计；批量操作直接一条 UPDATE。

负责人变更通知要求“业务更新、逐条审计、待发送记录”同事务完成，因此后续应抽出统一负责人变更服务，所有入口共用，而不是从 `audit_logs` 事后轮询推断事件。

## 5. 数据库实际状态

### 5.1 路径与连接

已提交版本把数据库固定为：

```text
server/data/app.db
```

当前工作区已增加 `DB_PATH` 环境变量，未设置时仍回退到上述路径，并在连接创建时执行：

```sql
PRAGMA foreign_keys = ON;
```

同时启用了驱动的外键选项。该改动未提交，不能写成线上事实。正式基线要求每个连接建立后开启外键、启动时验证、测试中断言，并在迁移后执行：

```sql
PRAGMA foreign_key_check;
```

外部 `sqlite3` 新连接查询到 `PRAGMA foreign_keys = 0` 只表示该新连接的默认值，不代表应用进程中的连接状态。

## 6. 现有业务流程与权限事实

### 6.1 线索创建

普通登录用户可以在请求正文传入任意 `owner_id`。后端仅在未传时默认当前用户，没有验证目标用户是否存在、启用或符合分配规则。

这是开发前待确认业务规则：

- 方案 A：member 只能创建到自己名下；
- 方案 B：member 可创建给其他业务员，但后端必须校验目标用户存在、启用且符合业务规则。

不能只靠前端隐藏负责人字段。

普通新增线索无论采用哪种方案，都不发送微信通知。

### 6.2 数据可见范围

当前后端的实际读取范围比“member 仅看自己客户”更宽：

- 线索列表未强制 owner 条件，登录用户可请求全部线索；
- 线索详情未校验负责人；
- 跟进时间线未校验负责人；
- 线索池对登录用户开放；
- 审计和同公司关联记录可读取；
- 工作台和部分导出统计为全公司口径。

写权限相对更严格：member 多数情况下只能修改、删除或跟进自己负责的线索。

AI 数据权限不得继承上述宽松读取现状。第一阶段固定为：

```text
member 只能分析自己当前负责的客户及其跟进记录
```

管理员按现有管理权限和专用后端接口执行。前端提交的 `lead_id`、`owner_id` 或客户上下文都不能替代后端授权查询。

### 6.3 负责人变更

现有入口包括：

- 单条编辑 owner_id；
- 批量 transfer；
- 公海认领给自己。

单条编辑会在真实变化时写 transfer 审计；公海认领当前工作区会写 transfer 审计。批量转移只执行批量 UPDATE，没有逐条读取旧负责人、没有逐条 transfer audit，也不能为每条真实变化生成稳定幂等键。

通知上线前必须统一为：

```text
读取旧负责人
→ 权限和目标用户校验
→ 更新负责人
→ 逐条写审计
→ 按规则写待发送通知
→ 提交事务
```

负责人通知条件是：

```text
原负责人 != 新负责人
并且
新负责人 != 当前操作者
```

操作者可以是管理员或业务员。公海认领给自己、转移给自己、重复提交相同负责人均默认不通知。

### 6.4 跟进与派生时间

新增跟进时会：

- 写 `follow_ups`；
- 把当前时间写入 `leads.last_follow_at`；
- 把本次 `next_follow_at` 写入 `leads.next_follow_at`；
- 同步当前 status。

但编辑跟进不会重算线索主表；删除跟进也不会重算 `last_follow_at` 或 `next_follow_at`。当最后一条跟进被删除时，还需要明确是否恢复此前手工填写的下次跟进日期，目前没有来源字段可以可靠区分。

第一版约定跟进逾期依赖 `next_follow_at`，因此该一致性问题是上线前置修复，不能留给通知模块静默猜测。

### 6.5 站内通知现状

`GET /api/notifications` 当前实时拼接两类数据：

- audit_logs 中转移给当前用户的记录；
- 当前用户 `next_follow_at < today` 的线索。

它没有持久化通知状态、渠道投递、重试、幂等或规则配置，不能直接承担微信通知队列。

## 7. 本次扩展的正确业务边界

### 7.1 不通知

以下操作不产生微信通知：

- 普通新增线索；
- 普通编辑客户资料；
- 联系人、手机号、微信号、来源、备注等普通字段变化；
- 标签、收藏、备忘变化；
- 查看和查询。

### 7.2 第一阶段通知事件

- `owner_changed`：真实转移且新负责人不是操作者；
- `scheduled_follow_overdue`：基于 `next_follow_at` 的约定跟进到期/逾期，按天升级；
- `visit_reminder`：独立未来拜访计划；
- `status_changed`：现有 status 的少量关键变化；
- `daily_report`；
- `weekly_report`。

`inactive_lead` 是基于 `COALESCE(last_follow_at, created_at)` 的长期未活动规则，必须与约定跟进逾期分开，默认关闭，不是首个 MVP 强制范围。

### 7.3 现有 status

第一阶段继续使用：

```text
新线索、跟进中、已报价、已成交、已流失、暂搁置、停止跟进
```

不增加 `sales_stage`、五级销售阶段字段或专用 API。咨询→需求确认→方案沟通→报价→成交只能作为以后经业务确认的可选优化，不能阻塞微信通知和 AI 助手。

### 7.4 拜访

`follow_ups.type = 拜访` 是已经发生的历史记录，不是未来计划。未来拜访需要独立 `visit_plans`，包含客户、负责人、时间、地址、备注和 planned/completed/cancelled 状态。

### 7.5 AI

AI 只做：

- 沟通总结；
- 需求和问题整理；
- 下一步跟进建议；
- 建议准备的问题和材料；
- 日报/周报文字总结。

AI 不做客户价值评分、成交概率、A/B/C 分类，不修改客户、负责人、状态或权限，不拥有数据库写入、Shell、文件系统或管理工具。

## 8. 关键冲突与推荐处理

| 当前问题 | 原因 | 推荐方案 |
| --- | --- | --- |
| 旧文档把普通微信改成企业微信唯一正式渠道 | 偏离老板主要使用普通微信的原始目标 | 普通微信为目标渠道，先独立 PoC；企业微信作为稳定备用和降级 |
| 旧文档把“24/48/72 小时无活动”称为跟进逾期 | 混淆 `next_follow_at` 与长期无活动 | 首版按日期处理约定跟进逾期；无活动规则独立、默认关闭 |
| 旧文档新增五级 `sales_stage` | 不是通知和 AI 的必要前置 | 第一阶段删除，继续使用 status |
| 旧文档要求 `supervisor_id` | 当前只有 admin/member，尚未确认主管层级 | 首版规则配置指定管理员接收人；确认正式主管关系后再加 |
| 批量转移无逐条审计 | 无法确认真实变化，也无法通知幂等 | 负责人统一服务和逐条事务审计是通知上线前置 |
| 跟进派生日期可能失真 | 编辑/删除没有同步主表 | 先修复和回归，再上线约定逾期 |
| 当前页面读权限过宽 | 历史 API 没有按 owner 强制隔离 | AI 使用更严格独立授权，不能继承现状 |
| 已提交版本固定默认管理员密码 | 空库自动创建 `admin / xyy123456` | 视为安全阻塞；当前未提交随机密码改动需评审、提交、部署和验证 |
| 已提交版本旧 JWT 保留角色 | 认证只刷新 is_active | 采用当前工作区的数据库实时角色方案并补测试，部署前核验 |
| 本地数据库与代码 DDL 不一致 | 缺正式迁移机制 | 备份、版本化迁移、外键检查和回滚演练 |

## 9. 后续扩展点

后续开发应在不破坏已有 API 的前提下增加：

1. 统一业务事件和持久化通知队列；
2. 独立通知 worker；
3. `NotificationChannel` 渠道接口；
4. 与主系统隔离的普通微信适配服务；
5. 企业微信应用和群机器人降级适配器；
6. 拜访计划；
7. 规则、绑定、发送日志；
8. 只读 AI 服务、三层权限和脱敏审计；
9. 确定性日报/周报统计。

所有外部微信或 DeepSeek 调用都必须在业务事务提交后执行。外围服务失败只能影响通知或 AI 请求本身，不能回滚或阻塞原线索业务。

安全不变量：任何 secret（JWT、DeepSeek、普通微信、企业微信或服务器凭证）都不得进入业务数据库、普通日志、前端包、通知正文或模型上下文。

## 10. 仍需业务确认

1. member 创建线索采用方案 A 还是方案 B；
2. “暂搁置”是否继续产生约定跟进提醒；
3. 约定跟进的提醒日级别、发送时间和升级接收人；
4. status 哪些变化默认开启通知、各自发给谁；
