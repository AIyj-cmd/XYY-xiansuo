# PC 管理后台与品牌数据域设计

## 1. 已确认需求

- 不再以移动端页面作为主要入口，H5 改为 PC 管理后台布局。
- 原线索业务字段、状态、筛选、跟进、报价、图片、标签、收藏、批量操作、负责人转移、软删除、公海和审计规则全部保留。
- 新增品牌、工商主体、多级品牌分类、网址资源，以及品牌/主体/线索之间的多对多关系。
- 工商主体保存统一社会信用代码、法定代表人、注册资本、注册地址、经营状态、成立日期和经营范围。
- 官网、招聘、工商来源和电商店铺保存网址、平台、标题、备注和首次采集时间。
- `admin` 与 `member` 均可增删改查品牌数据域；`member` 在界面显示为“业务员”。
- 线索权限保持原行为：业务员只能修改本人负责的线索，管理员可管理全部线索。
- 用户管理和线索批量导入仍仅管理员可用。
- 继续使用现有持久化 SQLite、WAL、外键和备份方案，不在本次改造中迁移 PostgreSQL。

## 2. 前端结构

主要入口为 `pages/desktop/home`，采用：

- 左侧固定导航
- 顶部搜索和操作区
- 桌面表格、筛选栏、分页
- 右侧详情抽屉
- 新增/编辑弹窗

桌面模块：

1. 工作台
2. 我的线索
3. 全部线索 / 公海待认领
4. 品牌管理
5. 工商主体
6. 品牌分类
7. 导入导出
8. 用户管理（管理员）
9. 系统设置

旧移动页面暂时保留为兼容代码，但不再作为登录后的主入口。

## 3. 数据模型

品牌域由 `server/src/brand-schema.ts` 幂等初始化，并使用独立的 `brand_schema_meta` 记录版本，避免修改已经发布且校验和固定的主迁移 001-010。

核心表：

- `brands`
- `companies`
- `brand_types`
- `brand_type_relations`
- `brand_company_relations`
- `resource_links`
- `brand_resource_relations`
- `company_resource_relations`
- `lead_brand_relations`
- `lead_company_relations`
- `brand_audit_logs`

所有核心实体均保留创建人、更新人、创建时间、更新时间和软删除标记。网址按规范化 URL 唯一复用，可同时关联多个品牌和工商主体。

## 4. 兼容策略

- 不删除或改写 `leads.company_name`。
- 新关系通过 `lead_brand_relations` 和 `lead_company_relations` 保存。
- 更新线索关系时可选择把首个关联品牌/主体名称同步到 `leads.company_name`，以兼容旧搜索、导出和外部集成。
- 原线索 API 和既有权限校验继续工作。

## 5. 权限

### 品牌数据域

所有已认证用户均可：

- 创建、查看、编辑、软删除和恢复品牌
- 创建、查看、编辑、软删除和恢复工商主体
- 管理品牌分类
- 管理网址资源
- 建立品牌、工商主体与线索关系
- 导入和导出品牌域数据

### 线索数据域

- 管理员：全部线索权限。
- 业务员：只修改、删除、恢复、跟进和调整本人负责的线索。
- 品牌关系写入沿用同一条线索所有权规则，不因品牌模块开放而放宽线索权限。

## 6. 数据安全与一致性

- 品牌域表启用外键并在服务启动后执行 `PRAGMA foreign_key_check`。
- 多表写入使用 `BEGIN IMMEDIATE` 事务。
- 删除采用软删除，避免破坏已有关系。
- 品牌名、工商主体名、统一社会信用代码和 URL 设置唯一约束。
- 品牌分类更新拒绝形成循环层级。
- 品牌域写操作写入 `brand_audit_logs`。
- Excel 导入按行事务处理，一行失败不会污染该行的部分数据。

## 7. 部署与回滚

部署前：

1. 使用现有 `scripts/backup.sh` 对生产 `DB_PATH` 创建一致性备份。
2. 在数据库副本上启动新版本并核对外键检查。
3. 构建 H5 产物后再切换应用版本。

回滚应用代码不会自动删除新表。旧版本会忽略品牌域表，现有线索表保持兼容。需要彻底撤销品牌域时，应先备份，再在离线维护窗口中按外键逆序删除新增关系表和实体表；默认不执行这一破坏性操作。
